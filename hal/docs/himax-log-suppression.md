# Himax 日志静默与功耗调查收尾

## 本次修复

`TrySuppressHimaxLogIfReady()` 旧实现把 `thp_afe_set_log_level` 当成十字节叶函数，
因此指令签名始终不匹配，异步初始化后的日志级别没有归零。

本机分析对象为 `C:\Program Files\Huawei\HuaweiThpService\himax_thp_drv.dll`，
SHA256 为 `F3C8376DF0B656E9FEFCEB7AD99B10AD0EC85C0A76237869C787D89FA5A8B063`。
以下为 dumpbin 对该文件的实际反汇编，均为 RVA：

- 导出入口 `0x41950` 是 `48 89 5C 24 10`，不是旧签名。
- 赋值序列在 **`0x424EA`**：`40 0F B6 C7 89 05 D4 D6 0E 00`。
  `movzx eax,dil` 后，`0x424EE` 的 RIP 相对写入目标为
  `0x424EE + 6 + 0xED6D4 = 0x12FBC8`。
  初始调查所述 `0x424ED` 偏移了三个字节，离线回归已检出并纠正。
- `0x28459` 的 `48 8B 0D 80 00 17 00 48 85 C9` 正确读取日志句柄 `0x1984E0`。

修复保留双签名、镜像大小和可写数据段检查；只有句柄非空后才用
`InterlockedExchange` 把级别归零，再原子回读。未知布局拒绝修改。
没有调用厂商导出、关闭句柄、改写代码段或修改磁盘 DLL。
`detail::SuppressHimaxLogInImage` 仅把已有逻辑分离为可离线测试入口，
参数契约是完整、已映射的 PE 镜像，不是任意外部字节流解析器。

## 日志门控与边界

`thp_afe_set_stylus_press` 位于 `0x2EC50`：

- `0x2EC73` 检查 `0x1983DC >= 3`，是设备生命周期状态，不是可关闭的日志标志。
- 状态错误日志在 `0x2EC83` 要求 level >= 1。
- 压力变化日志在 `0x2EEF0` 要求 level >= 4。
- 文件句柄读取点为 `0x2EDBB`、`0x2F02C`，均检查非空。
- `0x2F143` 更新压力值；置零日志级别不会绕过压力更新。

level 持续为零时这些日志跳过，不需要再调用 `thp_afe_set_log_level(0)`。
导出自身先记录日志再赋值，调用它没有更强的静默保证。

不能宣称一次置零使整个 DLL 永久零写入：

| 路径 | 证据 |
| --- | --- |
| 临时强制 level=2 | 写入 `F682/F70B/F7AD`，恢复 `F6B7/F734/F91E` |
| 正常级别设置 | `424EE` |
| 文件打开 | `2218E` 保存句柄，成功分支 `223EF` 无级别门控写入十字节 |
| 文件关闭或失败 | `223CD/2846B/29751` 清零句柄 |

临时设为 2 的窗口可能重新启用错误级日志，且存在与归零操作的并发恢复风险。
本轮按最小安全修复交付，不增加代码补丁、IAT 拦截或句柄置空。
宿主现有启动重试窗口仍是 30 次、每次 100 ms；超慢初始化和后续厂商重设级别
不由本次修复解决。

初始调查给出的 `logStatus=0x14B80` 在本机文件中不是指令边界，不能作为函数入口。
附近 `0x14C2D` 等位置存在 level >= 1 的状态日志门控，但尚未完成函数名称映射及
全部读引用的逐一控制流证明。已枚举直接写点，不能把它描述为全 DLL 静默证明。

## 验证与部署状态

- HAL Debug、Release 均经 `hal/scripts/build.ps1 -Verify` 构建通过。
  宿主 CHPE 非零，静态库为原生 ARM64。
- 主工程 Debug、Release 均经 `scripts/build.ps1 -Jobs 2` 构建通过。
- 两种主工程配置的 `ctest --preset arm64-<Config> -L device-free` 均 14/14 通过。
- `hal/scripts/test-himax-log.ps1` 在 Debug、Release 优化配置下运行离线回归。
  它用 SEC_IMAGE 映射实际 DLL，复制到私有内存，不运行 DllMain 或厂商触控链。
  覆盖真实签名、初始化等待、只修改级别、幂等、两个签名损坏、不可写段及小镜像。

运行中的 `OpenEGoHubService` 与 `OpenEGoHubThpHost` 都使用
`C:\Program Files\OpenEGoHub` 下的二进制。本轮未停止、重启、替换或修改它们。
产物位于 `hal/build/Debug`、`hal/build/Release` 与主工程对应 `build/arm64-*`。

用户结束手写后，按现有部署流程停止提供方、替换已安装的 `GaokunThpHost.exe`
为 Release 产物，再恢复主服务和触控接管。不要并行启动第二套提供方，也不要在
用户书写中执行部署。部署后应观察新进程的日志增长率、WriteFile 次数和同条件放电功率，
并验证压力、橡皮擦与恢复唤醒。未部署前不应宣称高频写入已在运行进程中消失。

## 功耗调查汇总

以下数字来自此前调查记录，本轮没有重新采样。进程累计 CPU 时间与磁盘字节不是
各进程的瓦数，不能据此严格量化或排序软件耗电。

- 手写活跃时整机放电 9.8–14.7 W，静止悬停或闲置约 5.77 W。
- 设计容量 45,076 mWh，当前满充 36,183 mWh，健康度 80.3%，循环 258 次。
  以满充容量除以稳定功率估算，活跃约 2.46–3.69 小时，闲置约 6.27 小时；
  这不是混合使用续航实测。电池容量下降约 19.7%，不等同功耗上升。
- 亮度 100%、2.5K 120 Hz LCD；此前背光贡献估计 3.5–4.5 W，
  不是本轮隔离测量。降低亮度是最直接可控项。
- 宿主累计 CPU 390 秒以上，集中在 TID 11864 的算法线程，优先级 15。
  日志 30 分钟内超过 85,000 次写入，观测窗口 WriteFile 约 214 次/秒；
  两者统计窗口不同，不应当成相同平均速率。
  Defender 累计 CPU 185 秒、读取超过 1 GB，与日志活动存在关联，
  但不能把全部开销归因于此。不要为优化日志而关闭 Defender。
- 手写时 OneNote 加 DWM 合计约 60%–75% 单核 CPU，是输入与显示渲染负载。
- OneNote 开机半小时累计写 8.31 GB、读 8.65 GB。
  12:39–12:40 对六个大型分区执行全量备份，合计约 8.3 GB：
  DataStructure 2.2 GB、Organization 1.7 GB、Network 1.7 GB、KMP 1.5 GB、
  LinearAlgebra 930 MB、Pre 250 MB。
  cache 17.92 GB，备份 14.89 GB；头四分钟诊断日志额外写入 48 MB。
  这是阶段性备份负载，不能按半小时吞吐外推全天。

建议优先调低亮度，其次在手写结束后部署日志修复，再检查 OneNote 备份频率与大型
分区安排。不要直接删除缓存或备份。修复前后应固定亮度、刷新率与书写工作量，
避开全量备份和本轮编译，才能判断日志修复的真实节能幅度。
