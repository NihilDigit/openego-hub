## 二、级序与数据契约

```
0  帧摄取          设备原始帧 + 采集时间戳
1  信号调理        基线、CMF                      → 差分图
2  峰检测          局部极大 + 幅值过滤             → 峰表
3  区域与接触点     种子遍历、质心、轴、尺寸、边缘量  → 接触点表
4  跟踪            按原始质心配对、id、保活、年龄    → 轨迹表
5  笔画            跨帧证据累积、笔画级判定          → 笔画表
6  上报语义        事件状态机、边缘修正、滤波、插值   → 上报表
```

级序与厂商同构,差别只在第 5 级——**厂商没有这一级**,理由见第六节。

**检测级跑在跟踪级之前,所以只能看到上一帧的轨迹。** 这不是缺陷,做检测层迟滞时
正需要这个输入。若把两级顺序调换,峰的轨迹锚点迟滞就要另找输入。

### 契约 1:两份坐标,方向不可逆

| 名字 | 谁写 | 谁读 |
|---|---|---|
| 原始质心 | 第 3 级 | 第 4 级(配对、加速度、边缘判定) |
| 上报坐标 | 第 6 级 | 第 6 级内部与对外 |

**第 4 级及以前不得读上报坐标;第 6 级不得写原始质心。**

这条是从二进制读出来的,不是从我们这边量出来的:厂商实现里这是两个字段(`+0x15e`
与 `+0x162`),`Peak_IDTracking` / `IDT_GetAcc` / `IDT_IsEdgeTouch` 读前者,`Filter_*` /
`Touch_CreatePostReport` / `TE_TouchDown*` 读后者(对这两个偏移的全量文本扫描,78 处
命中)。按它拆开之后,所有语料的断开数、笔画数、位置残差**逐位不变**。保留它的理由
是结构正确且有出处,不是因为它修好了什么。

### 契约 2:时间是量,不是帧号

第 0 级打一个真实时间戳,之后每一级都用它,不再有任何地方假设 1/120。

**优先级被实测下调了。** 这块面板的帧间隔中位 8331..8333 µs,与兜底的
`1/120 = 8333 µs` **逐微秒吻合**,p5..p95 只有 8229..8435 µs,每一万帧只有 1 到 6 个
超过 12 ms 的间隔,且全是笔画之间的秒级停顿。**接时间基是正确性问题,不是手感问题,
也不需要连带重标滤波参数。**

已接上的一半:`DeviceRuntime` 在构造帧处打主机接收戳(`receiveSystemEpochUs`,QPC,
启动时与系统时钟对一次表,取法见 `Common/include/SystemEpochClock.h`,工作台共用同一
锚点)。第 5 级优先读它。

促成这一步的是一次实测:第 5 级原先在拿不到戳时按自己被调用的次数推进时钟,而
**空闲帧根本不进管线**——`ProcessSignalConditioning` 在没有手指也没有存活状态时提前
返回。于是一次 660 ms 的抬起被数成一帧,两次点击并成一条笔画,当时正在扫的接续时间窗
因此几乎不起作用。**标定一个参数之前,先确认它真的在起作用。**

欠着的:采集时刻的戳(现在这个打在 `readMaster` 返回之后、管线之前,已不含 IPC 与
轮询抖动,但仍不是采集时刻),以及上报速率可配(`flash[0x38]`,厂商按 `1000/flash[0x38]`
算名义周期)——换档之后 1/120 兜底就不成立了。

注意 1-Euro 用的是速度**平方**项,不是教科书的线性项。三个参数(`m_minCutoff` /
`m_beta` / `m_dCutoff`)按平方响应标定,套用线性版的常见取值会让静止去抖和运动跟随
同时变差。

### 契约 3:拒绝是笔画级的决定,逐帧只允许记录证据

第 3、4 级可以往接触点上挂**证据**(尺寸、grip 比例、是否触边、信号形状),但不得
直接置「不上报」。要不要上报由第 5、6 级按整条笔画的证据决定。

理由是真机踩过的:在跟踪级之外置 `isReported = false` 会被跟踪级无条件重写,等于
没写;而已经建好的轨迹中途置位,会把贴边滑动掐断成一串 up/down。

**一处限定见第五节「五之三」**:第 3 级的掌判并不是「拒绝」,它是分割的输入,这条
契约在那个缝上无事可做。

### 契约 4:每级的输出是值,不是就地改写的共享缓冲

调理产物在 `touch.conditioned`,原始热图整帧不动。改这一条之前,「无 rawData 的旧录制
里 heatmapMatrix 已是调理后的量」这种情况要在重放工具里特判。

### 契约 5:量纲写在名字里

- `sizeMm` 不是测量值,是 `cbrt(signalSum) * scale` 的拟合值,区分不开「用力点的指尖」
  和「轻搭的掌根」;要物理尺度用 `areaMm2`(格数 × 间距,是测量值)。
- 传感器网格不是方形:列间距 4.5 mm、行间距 4.125 mm,按单值处理会让面积高估约 9%。

凡带量纲的字段一律带后缀:`...Cells` / `...Mm` / `...Px` / `...Us`。

**一处取舍:`TouchContact::x` / `y` 有意不改。** 它们的量纲从未被搞混过——全仓一律
是格——而改名要动两百多个调用点,让此后每个 diff 都更吵,换不到实测收益。DVR 格式里
的字段名同样不动,那是录制的模式,录制链路在重写范围之外。

## 三、各级的输入输出

### 第 3 级 —— 区域与接触点提取

输入:差分图、峰表、上一帧轨迹锚点。

**一个峰对应一次种子遍历,已落在别的区里的峰不再触发新遍历;一次遍历可以吞并多个峰。
所以一个接触点可以对应多个峰,但每个峰只属于一个接触点。** 遍历是标准 8 邻域、队列
驱动,不是名字容易误导的 `TZ_DFSProcess`——那个做的是肥手指/多指判定。遍历之后对
区域标记图做一次膨胀加一次腐蚀。(出处 `SPEC_zone` 一)

每个接触点必须携带:原始质心(格)、`areaCells`、`signalSum`、长短轴与角度、
`sizeMm`(拟合)与 `areaMm2`(测量)、**边缘信号累加器四个**(最外一圈与次外一圈,
两轴各一对)、由它们算出的 **`gripRatio` 两个**(每轴一个)。

`gripRatio` 是一等信号,不是边缘补偿的内部变量:它是「接触点被边界切掉多少」的可
观测量,边缘补偿、边缘拒绝、掌判都应当读它。

### 第 4 级 —— 跟踪

输入:接触点表(读原始质心)、上一帧轨迹表、时间戳。
职责:配对、分配 id、保活、维护年龄与速度。**不做任何上报决定。**

### 第 5 级 —— 笔画

厂商实现里没有这一级:`GripFilter_GetStage` 每帧重算,输入是上一帧状态而不是笔画
起始状态,只靠状态机与一道回退闸门约束跳变,**没有任何笔画级锁定**(出处 `SPEC_grip` 七)。

#### 为什么它是关键路径

掌抑制、按下侧迟滞、上报语义三件事都堵在它后面。有实测证据:把弱信号闸门挂在**轨迹**
上,离线拟合能压掉 91% 的掌误报,实时只剩三分之一,而碎片化更重(断开 14 → 163)。
原因是**一条真实的按压在跟踪级会碎成十几条短轨迹**,各自积累、各自判定。

#### 笔画身份与轨迹 id 解耦

轨迹会断,笔画不该断。跟踪级的 id 在失配超过重连窗口之后就释放并复用,而一条笔画
应当跨过:轨迹进入静默空档又回来(同一条)、轨迹被判终结但很短时间内在很近的位置又
冒出新轨迹(**同一条**)、手指抬起后重新按下(两条)。

接续判据三条同时成立才接续。**100 ms 是量出来的**:手势语料上碎裂的四对轨迹间隔是
50 / 58 / 67 / 75 ms,而真正的两次点击间隔在 200 ms 以上,**75 与 125 之间没有样本**。
扫参也验证过这道边界——400 ms 那一档开始把四边语料角上的重复点击并掉(37 → 30),
那正是不该并的。距离与尺寸比仍是未标定的初值。

#### 笔画携带什么

```
身份   strokeId(自己的编号)、组成它的轨迹 id 列表
时间   firstSampleUs、lastSampleUs、sampleCount、gapCount
位置   first/last、pathLengthCells、straightLengthCells
形态   maxAreaCells / maxAreaMm2 / maxSizeMm / maxPeakSignal —— 一律取迄今最大
邻居   同时存在的笔画数的最大值
边缘   是否曾经完全离开边缘带
判定   decided、verdict、decidedAtSample
```

**为什么取「迄今最大」而不是当前值**:我们的掌误报比真接触点更**小**(最大峰值信号
中位 508 对 1916),掌是碎成小片进来的。取当前值会让同一条笔画在强弱之间反复翻转,
取最大值才有单调性。

#### 判定时序:hold → decide → 粘着

```
证据已经够 → 立刻判有效并放行(不等采样数)
证据不够且采样数 < decide_max_samples  → hold(不上报,但不作废)
采样数够了仍不够                        → 判掌
判完之后                                → 粘着
```

**「证据够就立刻放行」是实测出来的,不是设计偏好。** 真笔画要等到第几个采样峰值才够
800:**中位 0、p90 0**,即绝大多数真接触点在第一帧就够,62 条里只有 1 条要等到第 14 个
采样。写成「先等 N 帧再判」会把这零延迟平白收走。

**hold 不等于 cancel。** hold 期间不发给主机但笔画还活着;随后判有效就补发一次按下,
位置用 hold 期间的第一帧。判掌则从未发过按下,也就不需要发抬起。

粘着**单向可翻**:判掌之后若「迄今最大峰值」越过门槛,翻回有效。这个量单调不减,
所以最多翻一次。契约 3 要禁的是反复改判,不是永不认错。不留这条口子的后果在真机上
出现过:手掌搭在屏幕上把拥挤度抬起来,旁边真手指的一次轻点被判成掌,这根手指在整个
接触期间**一直不响应**。

#### 输出给第 6 级的不是布尔,是阶段

```
Holding    还没判,不要发任何事件
Active     判为有效,按正常生命周期发 按下 / 移动 / 抬起
Cancelled  判为掌。此前发过按下就发一次 cancel,从未发过就什么都不发
```

### 第 6 级 —— 上报语义

**本级不判掌,只按笔画阶段发事件。本级不得回头改判**——若某条笔画的判定明显错了,
那是第 5 级的证据或阈值问题,在那一级修。「判据散在四处彼此覆盖」正是要消灭的病根。

事件模型采用厂商的七值枚举,其中 **cancel** 不是从 Chromium 借来的概念,厂商实现里
就有,只是复用了抬起分支下的一个子状态(出处 `SPEC_report` 二.2)。

本级还负责三处边缘处理,**三者互相独立,不要合并**:

1. **逐帧位置补偿** —— 按 `gripRatio` 把接触点放到最外一格内的正确亚格位置。已实现。
2. **移入修正** —— 做过,语料证明前提不成立,代码已删除,见 6.7。
3. **移出修正** —— 确认不用做:我们的收尾坐标中位就在边界上(0.00 格),厂商是
   0.12..0.14 格,边缘补偿已经做了这件事;它的另一半「把本该 cancel 的抬起转正」也
   已经是我们的语义,主机看见过的笔画一定收得到抬起。

## 四、有意与厂商分歧的地方

| 处 | 厂商 | 我们 | 理由 |
|---|---|---|---|
| 掌判粒度 | 逐帧滚动,无笔画锁定 | 笔画级判定一次 | 社区反馈集中在掌误触;逐帧翻转正是「写着写着跳一下」的来源 |
| 掌判依据 | 强度类判据 + 抓握分类 | 额外看**同时存在几条笔画** | 厂商没有任何「邻居数」参与判据;而实测强度类特征在笔画级切不干净,分布重叠 |
| 掌的整帧丢弃 | `loNum` 非零就把整帧上报清零 | 只压那一个对象 | 实测 771/783 帧是连坐,一个对象带走同帧另外三四个正常触点 |
| 角上的接触点 | 信号还有 476 就放弃 | 跟到信号真正归零 | 社区的抱怨正是手指够不到边 |
| 目标架构 | x64 | ARM64 原生 | 社区要摆脱的就是 x64 |
| 折叠屏/多形态 | 大量 `TSAFold_*` 分支 | 不实现 | 本机是单一形态,实现了也无从验证 |

**不照抄的东西也要写清为什么**,否则下一个人会以为是漏了。

## 五、已经修掉的缺陷

每条都有对拍数字,前三条另有真机确认。

### 1. 手指够不到边

根因:边缘补偿的 LUT 索引喂错了量——是**被补偿轴自己的 grip 比例**(最外一圈信号和
÷ 次外一圈,×16),不是次轴归一化位置。常量真值 full = 1.0 格、blend = 0.25 格,
移植值被反向调过两次;近端与远端用**不同的** profile 表,我们的四份是相同的占位符;
边界应从参数表读,不是标称网格。

| 量 | 修正前 | 修正后 |
|---|---|---|
| x 可达范围(格) | 0.418 .. 59.582 | **0.004 .. 59.996** |
| x 残差 中位 / p95 | 0.250 / 0.469 | **0.112 / 0.362** |

厂商在同一批帧上能到 3/2559 像素,即已追平。

### 2. 笔画中途断开

根因**不在跟踪级**:轨迹保住了,但重连窗口内生成的接触点 `isReported` 写死为 false,
手势层还另有一条 `lifeFlags & TouchLifeSilentGap` 的判据再压一次。对主机而言就是接触点
消失又出现。

诊断方式值得记下来:把断开空档里的每一帧翻出来,看接触点**是不在了,还是在但没上报**。
四边语料 183 个空档帧里,接触点仍在管线输出里的有 183 帧,完全不存在的 0 帧。这一句话
就把问题从跟踪级挪到了上报级。

改动两处:重连窗口内照常上报(`touch.tracking.report_during_gap`,默认开),手势层
不再重复判定。空档帧的上报位置**停在最后一个真实位置,不外推**——外推只用于匹配,
那里越准越好;上报越保守越好,否则手指真抬起时指针会继续滑出去几帧。

四份语料 11 / 62 / 65 / 746 → **全部 0**。

### 3. 手指停在角上消失

两步,第二步才是根因。

**第一步(止血)**:基线的冻结判据是个闩锁——冻结只在 `localDiff > 305` 时成立,一旦
某帧跌破阈值,该格落进背景更新分支被快速吸收,基线随之抬高,下一帧的 delta 更小,
**再也回不到阈值以上**。角落接触点被两条边界同时切掉,信号只有正常按压的十分之一,
尤其容易触发。加了按上一帧轨迹锚点定位的维持门槛,且**只对距边界 2 格以内的轨迹生效**
(掌正好落在屏幕中间,这条限定让掌与手势两份语料一个数字都没变)。676 → 152。

三种做法都量过,只有这一种没有代价;逐格迟滞反而不如全局降门槛,因为**手指移动时不断
进入新的格**,新格没有冻结史。

**第二步**:`hasFinger` 不再是整帧门控。厂商是用自己算的帧极值判无触摸、硬件检测器
只是「与」进来的否决票(`SPEC_baseline` §3.2),我们此前把它当唯一依据。改成「本帧
自己的信号极值(扣共模)≥ 200 就当有触摸」。门槛扫过:100 更差,400 等于没开,200 最好。
152 → 68。

断崖的具体数值也量出来了:`ProcessNoFinger` 的基线更新是 alpha shift 3、步长上限
**512**,角上一个 500 量级的信号一帧就能被推平,不可逆。覆盖是自限的,不需要计时器:
`ProcessFinger` 的背景分支与 `ProcessNoFinger` 用的是同一档速度。

**第三步**:剩下的 67 帧,信号在、宏区在,就是出不来接触点。逐个关掉峰检测的过滤试,
只有关掉 Z8(孤峰)过滤能救回。Z8 的判据是「峰值 ÷ 32 比周围一圈的和还大就当噪声尖刺」,
而**贴角的接触点只有三个邻居在面板内**(中间是八个),那几格本身几乎没信号——判据
按位置歧视。先试的「按实际邻居数把和折算回一整圈」**没用**(和本来就接近零,乘 8/3
还是够不着),改成迟滞才行:邻域被边界切掉、且上一帧确实有轨迹压在这里,就不当噪声。
68 → **1**。

### 4. 一根拇指裂成两三个接触点

拇指靠着掌滑动时,接触斑不是一个圆点,会分出两三个脊。近峰鞍点过滤的门槛太松:两个
1520 的峰只要谷降到 1398(8%)就都留下,于是同一根拇指出两三个接触点,而且**轨迹号在
它们之间来回换**——主机看到的是几根手指在原地抖。

门槛从 8% 提到 50%、半径 2 → 3,两个参数一并绑进配置(此前根本不可配)。拇指语料的
双点帧 88 → 12、断连 2 → 0。真双指不受影响:`012458` 的双点帧 2081 → 2074,上报帧数
与首次出现数一格未变,而那份录制里两点最近到 0.7 格,并非只有远距样本。断连数在其余
语料上一并下降,最明显的 `142120` 是 376 → 288。

## 六、试过并失败的

**动手改之前先读这一节。** 每条都是真机或对拍上试过并撤回的做法。

### 6.1 级序与数据流

- **边缘拒绝的判定要在跟踪之前,后果必须留到跟踪里执行。** 曾经写成在 `EdgeRejector`
  里直接 `isReported = false`,被 tracker 覆盖掉,等于没写。同一处还有个 `tc.state == 0`
  的守卫,本意是「只在落下那一帧拒绝」,但该级跑在 tracker 之前、`state` 恒为 0,条件
  恒真。**两个错误互相抵消,整个 `EdgeRejector` 是死代码,长期没被发现。**
- **拒绝只能在建轨迹那一帧生效,不能逐帧压制。** 建好轨迹之后再置位只能压住第一帧;
  而如果已跟踪分支也看这个标记,**贴边滑动会被中途掐断成一串 up/down**。
- 直通模式(`m_bypassStateMachine`)没有跨帧状态,「只在落下时拒绝」无从表达。这是
  已知的语义不等价,不是遗漏。

### 6.2 参数被改坏的历史

- **笔侧 IIR:方向搞反 + 阈值拉低。** 书写模式平滑从 `(6,18)` 改成 `(18,26)`,
  `m_speedMax` 从 140 拉到 60,悬停对被交换成 `(10,6)`。关键是**系数越大 = 新样本占比
  越高 = 平滑越弱**,交换等于把方向弄反。净效果是滤波永久停在最弱档(81% 原始直通),
  笔迹发抖。
- **触摸侧 IIR 收紧过头会出锯齿。** `(10,24)` 真机可见锯齿,已回退到 `(6,18)`。
  **剩余延迟不能靠收紧滤波拿,只能靠预测外推。**
- **掌框外扩的 `applyConfig` 回退值与成员初值不符**(9/10 对 1/1),配置缺键时掌框外扩
  面积缩到约九分之一。这类「三份字面量」漂移由 `SolversUnit_PipelineDefaultsConsistency`
  守护,**新架构必须保留同等的守卫**。

### 6.3 坐标输出的两个跳变

- **锁释放必须同时清偏移。** AFT 落笔锁释放时如果留下 offset,后续减法无条件执行,
  整条笔画被平移大约一个阈值。这个 bug 在阈值填错(X 轴 0.10 mm)时是潜伏的,改回原厂
  值(0.50 mm)之后才显现。
- **拖动 slop 不能永久保留。** 进入 Dragging 时回退一个阈值是为了不跳变,但永久保留
  这个偏移在**绝对定位**下意味着指针永远够不到起手方向那一侧的屏幕边缘。Chromium 扣掉
  首个 scroll delta 的 slop 没问题,是因为那边是内容相对滚动。正确做法是在若干帧内把
  偏移消解掉。

### 6.4 笔画级弱信号闸门挂在轨迹上

离线按笔画的峰值上限拟合,门槛 1050 能压掉 91% 的掌误报、误伤 9/54。实时开启之后:

| 变体 | 掌:只有我们报 | 掌:笔画/断开 | 手势:只有厂商报 |
|---|---:|---|---:|
| 关闭 | 1521 | 326 / **14** | **0** |
| 越过即永久放行 | 1024 | 501 / **163** | 0 |
| 第 4 帧判一次,两向粘着 | 970 | 506 / **170** | **89** |

**实时的轨迹比离线重建的笔画碎得多**,掌上偶发的强帧会让各个碎片分别放行。第二个变体
更差,因为它给**每一条**笔画的头几帧都加了延迟。判据方向是对的(弱 ⇒ 不是手指),
但必须在有真正的笔画抽象之后再做。

判据后来落到第 5 级(`touch.stroke.hold_min_peak_signal`,默认 800),挂在轨迹上的那套
`touch.tracking.stroke_hold_min_peak_signal` 与配套的判定帧数已经删除。

### 6.5 照抄厂商「判无触摸时不清差分图」

规格查清:厂商判「本帧无触摸」时不清差分图,只打开基线更新的闸门。照着改之后四份语料
一起变差(掌语料断开 22 → 49),而它本来要救的 67 帧漏报**一帧都没恢复**。

原因是两边的「调理后输出」不是同一个东西:厂商的 dif 是原始差分,后面还有 CMF、峰检测
逐级筛;我们的输出是**已经过阈的图**。在一个结构不同的管线里对齐单独一处,等于把噪声
直接送进下游。

**取证出处只说明厂商怎么做,不说明放到我们这里也对。**

### 6.6 把逐帧掌判改成「只记证据」

契约 3 说拒绝是笔画级的决定。照此改造第 3 级的掌判,四种改法全部撤回。

**第一件事:逐帧掌判根本不是「拦截」,它是分割的输入。** `ZoneExpander` 的
`AllowContactPeak` 有三处调用,其中种 zone 的那一处才是全部效果所在:被判掌的峰不种
zone,整块掌于是没有 zone,也就没有接触点。把另外两处放开,四份语料逐帧结果**完全
不变**。这里没有一个「丢弃接触点」的动作可以改写成打标记。

放开种 zone 那一处的代价是掌被切成几十个小 zone,其中最尖的一个反而被分类器判成手指,
证据无从附着(掌语料里出现过一条 1127 帧、零掌证据的笔画)。

**第二件事:掌框盖过分类器,而分类器在掌框里没有分辨力。** 拇指语料前半段 761 个有
宏区的帧里 293 帧一个接触点都出不来,查下去是 765 个峰判 PalmLikely、另有 109 个峰
**被判成 FingerLikely 之后又被掌框盖掉**。让掌框放过 FingerLikely 的峰,空帧减半
(293 → 140),代价是掌语料上报帧 21 → 5222。再给放行的峰记掌证据交笔画层数票,或改用
位移脱身(掌不动、拇指在滑),掌语料最好也只回到 1313,而拇指的**上报**帧数纹丝不动。

**改造之前先确认那一级到底在做什么。** 真要分开拇指与掌,缺的是特征而不是级序:峰的
尖锐度是对 5×5 均值求的,掌把邻域均值抬起来之后,靠着掌的拇指和掌自己的脊线不可分。

改动的完整 diff 在自动备份 ref `refs/claude-autobak/20260824-165419`。

### 6.7 移入修正:有语料,且语料证明前提不成立

移入修正的前提是「手指进屏幕时已经在快速移动」。`dvr20260824_095432`(从四边外侧滑入,
左 2 右 4 上 4 下 2)实测入界速度只有 **0.02..0.41 格/帧**,而厂商自己的判据是连续两步
各 ≥ 50 px(≈1.17 格)——**那条判据在这台设备上同样不会触发**。而且也不需要:起手位置
本来就落在距边 0.00..1.19 格。

打开它只有三条笔画被改到边界,代价却是确定的:判据要三个采样,贴边起手一律推迟两帧,
角上的点击每次都付。**代码已删除**,重启这条要先录一份入界速度够得上判据的语料。

### 6.8 空闲门控不要动

查角上漏报时改过管线的空闲门控(自己的信号够强就把整条管线跑完)。看着合理,实测
**笔 + 掌语料从 404 帧上报涨到 1619 帧、中途断开 6 → 84**,而对那 67 帧一点用都没有
——峰检测修好之后接触点根本不会死,存活状态一直在,管线自己就会继续跑。已撤。

### 6.9 掌闸门被真机否掉过一次

对拍数字全是好的,真机的回答是**「有迟滞,而且不一定响应」**。两个症状各有出处:
迟滞来自「够不到门槛的接触点要等满 `decide_max_samples`」;不响应来自「判掌之后粘着」。
后者已改成单向可翻(见第三节)。当时默认改回 0,后来在新语料上重标才回到 800。

**重新标定这个闸门时,基准应当是真机而不是语料**——语料在这件事上已经错过一次。

## 七、怎么验证

### 干活的循环

每改一步,跑这三条,顺序不能换:

```powershell
pwsh -File scripts/verify.ps1        # 停服务 → 构建 → 查头文件依赖 → 测试,任一步失败即止
.\build\arm64-Debug\DvrReplay.exe --dataset <语料.dvrbin> --out ours.csv
python scripts\oracle_compare.py <对应的 oracle.csv> ours.csv
```

**不要绕开 `verify.ps1` 单独跑 `ctest`** —— 构建失败后 ctest 会在旧二进制上跑出全绿。

`verify.ps1` 会在头文件依赖失效时自动重新生成构建目录。注意它重新生成之后
**`DvrReplay.exe` 需要单独再建一次**(不在默认目标里)。

### 对拍三步

```powershell
# 1. 把录制里的设备原始帧摊平导出(ARM64,仓库内)
.\build\arm64-Debug\DvrReplay.exe --dataset <x-session.dvrbin> --dump-frames --out frames.bin

# 2. 用厂商实现跑一遍(x64,仓库外)
C:\Tools\re\oracle\oracle.exe --in frames.bin --out oracle.csv

# 3. 我们自己跑一遍,然后比
.\build\arm64-Debug\DvrReplay.exe --dataset <x-session.dvrbin> --out ours.csv
python scripts\oracle_compare.py oracle.csv ours.csv
```

宿主源码在 `C:\Tools\re\oracle\`(未入库:它链接厂商二进制,只在本机有意义),
用 `vcvarsarm64_amd64.bat` 交叉编译成 x64:`cl /nologo /utf-8 /W3 /Zi /Fe:oracle.exe oracle.c`。
另有 `--probe-layout`(用单点信号确认缓冲区轴序)与 `--dump-stages`(导出逐级中间量)。

### 比什么、不比什么

比:每帧接触点数是否一致、笔画有没有中途断开、位置差。

**不比坐标的绝对值。** 两边的格→像素换算未必同构,脚本先用最小二乘拟合
`像素 = scale * 格 + offset` 再算残差。实测拟合出的 scale 与标称刻度相差不到 3%,
即两边坐标系本来就是同构的。

**笔画怎么数(这里错过一次)**:按 id 收集它出现过的帧号,再按帧号是否连续切段,
间隔 4 帧(约 33 ms)以内算同一条笔画中途断了一下,超过算两条。**不要写成「这个 id
以前出现过就算断触」**——id 抬起即回收,那样数会把「换了一根手指、复用了同一个编号」
当成断触。这个错误真发生过,而且差点导出反向结论。`DvrReplay` 自己打的
`mid-stroke reconnects` 有同样的缺陷,别拿它下结论。

### 一条限定,适用于所有对拍数字

宿主调用 `TSA_Processing(raw, ctrlFlags, ctx)` 时 **`ctrlFlags` 传的是 0**,而真实驱动
会传有意义的值。实测 `tsaStatic+0x10c` 恒为 0,即特性位图每一位都关着:子区功能、
按下阈值特例、自扫描 SSLo 判据三条分支都不走。

**所以所有「厂商如何如何」的数字,严格说是「厂商在可选特性全关的配置下如何如何」。**
这不使它们失效——两边跑的是同一份录制——但真机上未必相同。

决定不去补,理由:**没有判据**。靠猜几个值再重跑,每个猜测都会产生一份自洽的输出,
而没有真机对照物去判定哪一份才是华为实际跑出来的。要重启这条,前提是先找到能验证
猜测的判据。本机 `C:\Program Files\Huawei\HuaweiThpService\` 里没有任何模块引用 TSACore,
所以没有现成的调用方可以照抄。

### 量东西之前先验量具

基线表被推翻过两次,**两次都是量错而不是代码变了**:

1. 笔画计数把 id 回收当成断触。
2. 接触点串按逗号切,而那一列内部用**分号**分隔——只拿到第一个接触点,而单指语料
   照样 100% 吻合,毫无征兆。「多指分割只有四成吻合」这个错误结论在文档里存在了一小时,
   还差点据此把重写顺序排错。

`python scripts/oracle_compare.py --self-test` 用已知答案的输入守住这两条。
**凡是「某项指标特别糟」的结论,先确认量具数得对。**

### 三条纪律

- **凡是「某某只在 X 情况下发生」这类结论,先量一个运行期的值**,不要靠推理。
- **一次只改一处,改完就量。** 一次改动同时改善三项、恶化一项,只有分步量才分得清。
- **验收不是「所有指标都不许变差」,是「变差的指标必须用测量解释」。** 前者默认厂商
  永远对:第 1 级修好之后「只有我们报」涨了 257 帧,逐帧查过全是角上真实存在的信号,
  厂商自己丢了而我们跟到底。按「不许变差」会否掉一个真正的改进。

- `014239`(笔沿四边书写):我们上报 0 个触摸接触点是**正确**的,笔被压制了;厂商那边
  1377 帧全报成触摸,因为宿主没有给它喂笔的数据(`TSA_SetStylusData` 一族尚未接)。
- `013049`(掌 + 笔)同理,厂商把笔当手指。
- `013201` 只有 76 帧双方都有接触点,样本太小。

`dvr20260823_134028` 与 `134054` 重放出 0 个接触点,不要用。

**仍缺一份:固定间距双指**,给已知间距真值,用来验收多指分割与尺寸估计。

## 九、Future Work

按建议顺序。掌抑制已在真机上确认可用,**不要再动它**。

### 1. 清掉量纲不对的旧旋钮

- `TouchTracker::m_touchDownRejectMinSignal = 55` 比的是**区内信号总和**,而厂商那条
  判据比的是**峰值**(600,边界 420)。实测四份语料首帧 `signalSum` 最小 1400,是门槛的
  二十五倍,它只挡噪声,而且没绑进配置,想扫都得重编。机制已经在第 5 级用
  `hold_min_peak_signal` 实现了,这个该退休。

按契约 3,拒绝不该在建轨迹时就 `continue` 掉,那样笔画层根本看不到这个点。

### 2. 第 3 级重写

不是当务之急,剩下的是结构整理。

### 3. 契约 2 剩下的一半

采集时刻的戳、上报速率可配。实测对当前手感没有可测影响,是正确性问题。

### 4. 已降级为可选:第 4 级重写

测量不支持:

- 接触点数与厂商的分歧**没有一例是「我们比厂商少」**,而跟踪级碎裂产生的是多余的
  down/up 对,不抬高每帧点数。
- 我们的中途断开已经全部是 0。厂商的保活机制读出来也很简单:**槽位不删 + 速度冻结**,
  未匹配的 prevTouch 只结转不释放,不合成任何接触点(`SPEC_track2` §2.1、§5.4)。
- 厂商压低每帧点数的地方在**按下防抖**,那正是我们第 5 级闸门的对应物,不是跟踪级的事。

排除过一条可能的口径混淆:oracle 的 CSV 里只有事件码 2/4/64,没有事件码 1 的行,
即它导出的就是「厂商真上报的」,与我们的 `isReported` 同口径。

真要重写时用得上的两条:配对是峰层的**匈牙利全局最优**(我们已经是),门限是
`TS_MMToPixel(flash[0x888])` 的**固定毫米值,不随速度/尺寸/贴边变化**;新号用
`TE_GetNextID` **轮转**分配而不是取最小空号,天然带「最近用过的号不立刻复用」。

### 5. 外观问题:一帧里出现两个相同 id

抬起补发时,跟踪级滞留的同 id 接触点还在列表里,各语料 21–85 次。滞留的那个
`isReported = false`,主机会忽略,所以不影响行为。

### 6. 未收口的取证疑点

- `edgeFlag` 的位域定义未确认,实测 38 种取值。
- `g_tsaPrmtFlashConst` 的元素宽度未确认,边界真值(0.0 / 60.0 格)是按 `ushort` 读的,

## 十、工程环境:每一条都真实浪费过时间

### 头文件依赖会因编码静默失效

ninja 靠匹配 `/showIncludes` 的行首前缀抽依赖,CMake 在配置期把该前缀写进
`CMakeFiles/rules.ninja` 的 `msvc_deps_prefix`。这台机器只装了 2052 中文消息资源,
前缀是「注意: 包含文件: 」,而**两侧的编码可能不一致**:记录的取决于**配置时**的控制台
代码页,cl 的输出取决于**构建时**的代码页。

一旦不一致,每个 obj 的依赖记录都是空的:改头文件永远不触发重编,而求解层几乎全是
`.hpp`。**失败方式完全静默**:构建成功、测试通过、行为不变。出现过「测试报告成员值
0.08、源码写着 1.0」的矛盾,也出现过 `DvrReplay` 在 frame 0 死住(结构体加了字段,
只有部分 obj 重编,新旧布局混链),当时误判成新写的判定逻辑死循环。

判据很便宜:`touch` 一个求解层头文件再 `ninja -n`,回答 "no work to do" 就是依赖已经
失效。修法是**重新生成构建目录**,不是 `--clean-first`;`verify.ps1` 的 header deps 一步
会直接比对字节并自动重生成。不要试图用 `VSLANG=1033`,英文消息资源没装,该变量是空转。
不要按「有多少 obj 记了依赖」判断健康,那个数字只反映本轮重编了多少个。

删构建目录这一步在这台机器上会失败:`trash` 与 Bash 里的 `rm -rf` 都走
`windows-trash.exe`,对整棵 build 树报 `2147549183` 且**退出码为 0、目录原样留着**。
改用 `Move-Item build\arm64-Debug build\arm64-Debug.stale-<日期>` 挪开再重新配置。

### 构建被中断之后依赖不可信

Ctrl+C、LNK1168、锁 exe 之后 ninja 依赖库损坏,增量结果不可信,必须 `-Clean`。症状是
新旧对象混链:debug 迭代器处 AV、跨进程结构越界读到 0xCCCC、头文件改动「生效」却输出
旧行为。验证改动是否真编进去:对比 obj mtime 与头文件 mtime。

### 恢复文件会保留旧 mtime,ninja 认为不需要重编

`mv` 与 PowerShell 的 `Copy-Item` 都会。做反向验证(故意改坏、看测试变红、再改回)时
必然踩到:改回之后测试还是红的,看起来像是改回失败。恢复之后要 `touch` 一下,或者
干脆用编辑工具改回而不是拷贝备份。

### ninja 停了 ctest 照样绿

构建失败后 ctest 在旧二进制上跑出全绿。**判构建成败要看有没有 `ninja: build stopped`**,
不要只看有没有 `error`。服务 exe 被锁(LNK1168)恰好排在测试之前,这条最容易中。

### 其余

- 服务/工作台/托盘各锁一个 exe,链接前先停。`scripts/svc.ps1` 自提权处理,UAC 静默。
- **Release 构建经工具会卡死**,交给用户在自己终端跑。Debug 正常。
- `dev-cycle.ps1` 必须用 pwsh 7(无 BOM UTF-8 中文注释,powershell 5.1 解析报错),
  且需要管理员权限。`-Clean` 只建服务与工作台,测试可执行文件和 `DvrReplay.exe` 不在其中。
- 共享内存改布局要同步升 `kSharedFrameAbiVersion` 并更新 `static_assert` 数值,用探针
  打印实际 sizeof/offsetof;服务与工作台必须同批重建。
- DVR 新增帧字段不要进 `ValidateCriticalRequiredFieldsPresent` 名单,否则旧 `.dvrbin`
  全部报废;`TryRead*` 默认值兜底是设计好的兼容路径。
- `FixedVector::clear()` 只重置长度,旧对象留在底层数组,每帧字段必须无条件写。
- `CommonPenStatusChannelTest` / `CommonPenControlChannelTest` 在托盘运行时失败(内核
  对象争用),不是回归,停托盘重跑即绿。
