# 触控提供方的时间常数与生命周期

触控提供方在 EGoTouch 与 HuaweiTHP 之间切换，切换由托盘的租约驱动。这份文档记录这套机制
在真机上的实测数字，以及据此确定的设计。

测量环境：GK-W7X（MateBook E，GaoKun 平台），Windows 11 ARM64，2026-09-03。以下每个数字都是
本机实测，不是推算。

## 服务与提供方的切换耗时

| 动作 | 实测 |
|---|---|
| `HuaweiThpService` 启动到 RUNNING | 323 / 325 / 341 ms |
| `HuaweiThpService` 停止到 STOPPED | 1640 / 3350 / 3368 ms |
| 本服务正常停止（含交还华为） | 6331 ms |
| 一次完整接管占用控制线程 | 4888 / 5129 ms |
| THP 宿主停止 | 约 4.4 s |

两个数字决定了不少设计：**华为起来只要 0.32 秒**，交还它的代价远低于此前的估计；而**一次接管
本身要花掉 5 秒左右**，比租约超时（5000 ms）还长。

`HuaweiThpService` 处于 START_PENDING 时发停止命令会被 SCM 拒绝，服务继续走到 RUNNING。这个
窗口里 `SwitchToEGo` 会走 `stopHuawei` 失败分支，接管失败但华为确实在跑，状态没有失真。

## 原厂停止耗时的分段实测（2026-10-13）

在本机停止 OpenEGo 主服务、确认触控宿主已停止并退出后，单独测量原厂服务。
停止请求在独立线程调用 `ControlService(STOP)`，同时每 10 ms 查询服务状态和进程是否退出。
以下时间均从发起停止请求算起，查询结果有轮询与调度误差。

| 停止请求时间 | ControlService 返回 | SCM STOPPED | 进程退出 | 日志中的 ThpStop before → after |
| --- | ---: | ---: | ---: | ---: |
| 10:04:47.081 | 10.8 ms | 3453.1 ms | 3498.9 ms | 3417 ms |
| 10:05:01.454 | 2.6 ms | 3308.3 ms | 3339.8 ms | 3296 ms |
| 10:05:08.576 | 3.5 ms | 2119.2 ms | 2142.5 ms | 2107 ms |

第一轮使用主服务退出时恢复的原厂实例；后两轮重新启动原厂，分别在 RUNNING 后等待
10 秒、3 秒再停止。两次重新启动到 RUNNING 为 847 ms、776 ms，不能将早先的约
0.32 秒视为固定启动耗时。实验结束后恢复 OpenEGo 主服务及宿主，确认原厂为 STOPPED、
两项 OpenEGo 服务为 RUNNING；未测量首个可用触摸报告的时刻。

原厂日志显示，绝大部分停止耗时发生在 `ThpStop before` 和 `ThpStop after` 之间。
之后才依次出现 `Vhf_Stop`、`Usb_Stop`、USB 读线程退出、`SpiMonitoringStop`，这些日志
在各轮中相隔仅数毫秒。因此慢点不在本项目的 100 ms SCM 轮询，也不主要在进程最终退出。
交接前提前启动宿主进程，无法消除这段 DLL 内部等待。

对本机零售版 `ApDaemon.dll` 做静态反汇编，进一步确认：

- `ThpStart` 在 RVA `0x4235` 调用 `CreateThread`，入口 `0x4170` 调用 `ThpMain`，
  线程句柄保存在 RVA `0x1694A8`。
- `ThpStop`（RVA `0x42F0`）先设置停止标志，并调用对象的虚函数通知它；在 `0x43A1`
  设置等待时间 `0xDAC`（3500 ms），随后于 `0x43AD` 调用
  `WaitForSingleObject`，等待的正是上述线程句柄。
- 等待返回值没有被检查，后续直接关闭句柄。因此这个 3500 ms 是等待上限，不能称为
  固定休眠，也不能以 `ThpStop` 返回证明工作线程必定已经退出。

该文件 SHA-256：`E10C0694196213E27B8B4CC64E8D529E1147C8E9BF2D5B5D59D513C7EA699AB0`。
静态逻辑与实测耗时相符。后续线程采样与修复见下文；设备实际释放时刻仍未测定，
不能据此提前并行启用第二条触控链。

本次原始记录位于本机 `temp/thp-stop-20261013-b/`，探针为
`temp/measure-thp-stop.ps1`，均为不提交的实验产物。首次隔离时发现服务 STOPPED 后宿主
进程短时间仍在，因此那次测量被取消并恢复服务；上表只包含后续隔离成功的三轮。

### 后续定位：清理线程持锁休眠（同日）

进一步隔离原厂服务，以 x64 探针读取工作线程句柄、对象虚表及线程栈内地址。
本机 ARM64/x64 混合栈未能通过 `StackWalk64` 完整展开，因此栈扫描中的地址只作为候选
返回地址，结合静态调用点核对，不当成完整调用栈。采样需要短暂挂起线程，耗时数据受其扰动。

实测对象虚表为 `ApDaemon+0x123C00`，`+0x40` 指向 `0xC09B0`；函数中的字符串为
`PreTp::Process`。停止后的多次采样持续出现返回地址 `0xC1ED2`，其前一条调用是
`pthread_cond_wait(object+0x530, object+0x528)`。约 2.6 秒后进入后续析构阶段，
全局对象指针清零，再过约 0.6 秒工作线程退出。

退出通知的完整路径不是直接返回，也不是漏发通知：

1. `ThpStop` 置停止标志后，调用对象虚表 `+8`（`0xBF420`）。
2. 停止标志让它跳到 `0xC0923`，经 `0xCBF20` 创建清理线程，线程包装函数
   `0xCC090` 调用 `0xBDE70`。
3. `0xBDE70` 清除对象运行标志（`+0x56B`），取得互斥锁（`+0x528`），广播条件变量
   （`+0x530`），释放锁；随后检查工作线程退出标志（`+0x56C`）。
4. 退出标志未置位时，进入最多 26 轮的重试。每轮在 `0xBE944` 调用加锁包装函数，
   `0xBE950` 广播条件变量，`0xBE95B` 调用 `Sleep(100)`，**到 `0xBE96A` 才解锁**。
   被唤醒的线程需要重新取得这同一把互斥锁，才能从条件变量等待返回。

这段持锁休眠是主要延迟来源，已做单变量对照：只对隔离的原厂进程内存，将
`0xBE956` 的 `mov ecx,100` 参数改为 `1`，不修改磁盘 DLL，不改变外层 3500 ms 超时。
修改前核对该位置完整的 11 字节指令；实验进程随后停止，恢复路径重新启动原版进程。

| 情况 | 原厂日志 ThpStop before → after |
| --- | ---: |
| 修改前，10:30:02.658 → 10:30:05.967 | 3309 ms |
| 临时 Sleep(1)，10:33:45.524 → 10:33:46.127 | **603 ms** |
| 恢复原版，10:33:47.257 → 10:33:50.546 | 3289 ms |

临时修改一轮中，212 ms 采样时对象指针已经清零，647 ms 采样时服务 STOPPED 且工作线程
已退出。对照支持「清理线程持锁休眠阻碍工作线程退出」这个解释，推翻了「硬件必须花
三秒关闭」的猜测。没有测量真实输入的首帧恢复时间，也不能以单次对照证明缩短休眠在
所有睡眠、异常和设备状态下都安全。永久修改应优先修正同步顺序，而不是采用未经验证的
固定地址补丁；本次没有修改运行代码或安装文件。

原厂 VHF/USB/SPI 的停止仍在 `ThpStop after` 之后，因此这次实验不支持在旧链完成清理前
并行启用新链。另需修正就绪检查的设想：`hal/docs/thp-symbols.md` 已确认
`ThpFuncStart` 无条件返回 1，检查其返回值不能作为触控已就绪的依据。

原始采样在本机 `temp/thp-stack-20261013{,-b,-c}/`，对照在
`temp/thp-fast-unlock-20261013/`，探针源文件为 `temp/thp-stack-probe.cpp`。

### 宿主预载补丁尝试：已撤回默认应用

`hal/src/shared/ThpShutdownFix.h` 保留了一个实验改写：在 `ThpFuncStart` 之前，将已核验版本
`ApDaemon+0xBE956..0xBE96D` 的 24 字节指令重排为「解锁，再 Sleep(100)」。
Sleep 的 IAT 相对位移随调用位置调整，指令区间长度、100 ms 间隔、26 轮重试和外层
3500 ms 等待均保留。它没有使用实验中的 Sleep(1) 参数。**宿主已不再调用它**；
后续系统错误日志表明，仅看停止耗时不足以证明收尾安全，见下一节。

应用前同时核验 DLL 文件 SHA-256 和完整原始指令序列；不支持的版本继续使用原逻辑。
补丁只存在于宿主进程内存，不改原厂文件。写入后恢复页面保护、刷新指令缓存并回读校验；
写入失败尝试恢复原指令，无法恢复时终止进程以免执行半条补丁。曾接入宿主时，
一般应用失败会拒绝启动并走提供方回退。已应用的序列重复检查为成功，不重复改写。

当时两轮设备测试中，宿主启动后持续运行 8 秒，SCM 均报告停止，耗时分别为
641 ms、672 ms。原厂仍未经修改，停止耗时 3359 ms、3328 ms；整次接管分别为
3641 ms、3578 ms。**这不能等同于正常收尾，也未解决亮屏时原厂停止的延迟**。
没有用实际手指/笔输入确认首帧恢复，也未完成睡眠循环测试，不能声称唤醒空窗已消除。

运行中修补原厂的候选实现已撤回：虽然内存回读正确，普通控制程序中的退出仍多次约
3.3 秒；成功探针去掉符号初始化后也恢复为慢退出，但单独把符号初始化加入控制程序
不能稳定复现提速。该差异尚未查清，不能把探针结果直接当作生产调用链结果。

验证包含 Release ARM64EC 构建、改写后 x64 指令反汇编、上述真机两轮，以及
`hal/tests/ThpShutdownFixTest.cpp` 的未知文件、不同文件哈希、指令不匹配、写入结果、
页面保护恢复、幂等和边界保护检查。此测试只修改本进程的私有分配区，不启动厂商链；
用本机支持的 `ApDaemon.dll` 路径作为唯一参数。接管协调器现有回归测试也通过。
这些检查验证改写的保护条件，不验证厂商链的退出安全性。原始整链结果在本机
`temp/thp-localfix-final/`。已安装宿主没有被替换，实验改写的默认调用已撤回。

### 原厂继续研究：代码更新与 AFE 收尾是两层问题

后续实验使用隔离进程或原厂程序副本，所有服务路径最终恢复。没有覆盖原厂安装目录中的
DLL。以下均为同机 2026-10-13 的结果，不能作为已完成的生产修复。

**运行中读回的代码不一定是实际执行的代码。** 在同一探针、同样暂停线程和刷新指令缓存的
条件下，原指令、Sleep(1)、先解锁再休眠三组原厂停止时间分别为 3344、3344、3329 ms。
通过导入表只记录指定 Sleep 调用后，发现代码区已读回 Sleep(1)，实际传入的仍为 100 ms；
重排后的新返回地址也没有被命中。这符合模拟执行仍使用旧指令的表现，但尚未定位具体缓存
机制，不能把某个 Windows 刷新 API 视为已经验证有效的解决方法。

仅在该调用点通过导入表把参数改为 1 ms，曾得到 985 ms 的正常进程退出；后续整链测试出现
访问异常。把 26 轮休眠缩短也改变了内层等待预算，因此该方法没有保留为正式实现。

**加载前修改同样暴露了后续收尾问题。** 将原厂程序完整复制到隔离目录，核对加载的 DLL
路径，再临时调整服务 ImagePath 进行对照：

| 副本改动 | 原厂停止 | 原厂停止请求 → 宿主报告启动 | 结果限制 |
| --- | ---: | ---: | --- |
| 无改动 | 3531 ms | 3891 ms | 后查错误日志发现该对照副本也有访问异常 |
| 先解锁再休眠 | 625 / 3531 ms | 984 / 3781 ms | 未稳定提速 |
| 全局关闭时跳过内层轮询，保留外层等待 | 3546 / 594 ms | 3906 / 844 ms | 仍有超时；不能上线 |

最后一种只把 `ApDaemon+0xBDFBD` 的 `jne 0xBE93C` 改为 `jne 0xBE97B`，条件仍是
全局停止标志，其他情况下的轮询不变。这是诊断变体，不是已接受的修复。

**停止请求没有丢失；后续析构仍可能失败。** 对该变体的三轮只读采样中，停止后约 16–31 ms
就观察到全局停止标志为 1、对象 active 为 0、exited 为 1；约 110 ms 时全局对象指针清零。
其中两轮主线程到 3500 ms 期限仍未结束，另一轮约 594 ms 结束。不能把对象指针清零当成
底层库已经完成收尾。

慢退出案例在约 1200 ms 的原始栈中出现 `ApDaemon+0xE253A`，其前一条是
`ThpBase::UninitAfe`（函数名来自二进制字符串）调用对象 `+0xBB0` 函数指针的指令。
栈扫描未完整展开，地址属于候选返回地址；真正的异常另由 Windows Application Error
事件确认：13:21:38、13:21:58 的故障模块为 `himax_thp_drv.dll+0x6A1F`，异常码
`0xC0000005`；13:31:08 的故障模块为 `ntdll.dll+0x1AC4A0`。

`himax_thp_drv.dll+0x6A1F` 位于 `hx_set_raw_data_type`，解引用由全局 RVA `0x184380`
取出的指针，没有判空。该指针在 `0x213B0` 接收 `MapViewOfFile` 的返回值；
`thp_afe_close` 在 `0x28E3F` 解除此映射，并在 `0x28E45` 清空指针。这把问题收窄到
映射及访问者的生命周期，但尚未捕获故障时的指针值，也没有完整证明具体竞争线程或
重复关闭入口，不能直接以加判空替代正确关闭顺序。

此 DLL 的 SHA-256 为 `F3C8376DF0B656E9FEFCEB7AD99B10AD0EC85C0A76237869C787D89FA5A8B063`。
系统还记录了 `SpiModule.x64.dll_unloaded` 的异常，已安装宿主和测试宿主的停止实验均有
原生异常记录。它们不能单独证明由本次补丁引起，也不能被 SCM STOPPED 掩盖。

**验证标准必须补上错误日志。** 13:21 的两轮探针返回进程退出码 0，但相同 PID 的系统日志
已经记录访问异常。因而“SCM 停止 + 退出码 0”并不足够，需同时检查原生异常、相关工作线程
及模块关闭完成，再验证真实输入和睡眠循环。此前把宿主补丁称作“已修复”过于乐观，已撤回
其默认应用，只保留实验代码及改写保护条件测试。

后续重点是核对“停止产生回调 → 等待访问者退出 → 解除映射、卸载 DLL”的实际顺序，
同时审计 SCM 停止、父进程看护和宿主析构是否重复执行收尾。当前证据不支持进一步缩短
外层等待或跳过 AFE 清理。服务注册路径、运行中的提供方及原厂 DLL 哈希均已恢复/核验。

本机原始材料：`temp/vendor-unlock-controlled/`、`temp/vendor-iat-controlled/`、
`temp/vendor-code-execution/`、`temp/vendor-iat-native-handover/`、
`temp/vendor-dll-controlled/`、`temp/vendor-selfwrite-controlled/`、
`temp/vendor-localstore-controlled/`、`temp/vendor-preload-controlled/`。
后者的 `state-*.txt`、`destructor-*.txt` 和 `crash-events.json` 可按 PID、时间关联。

### 回调、线程与释放顺序核对（2026-10-13）

本轮只读核对已安装的零售二进制、宿主源码和上述实验记录，没有再次停止服务或应用补丁。
以下地址均为各模块 RVA；静态存在的竞争窗口与已经捕获的崩溃分开记录。

**算法收尾早于外部通知源停止。** `THP_Service!ThpFuncStop` 的实际调用顺序为：

| 调用点 | 动作 |
| --- | --- |
| `0xE611` | 调用 `ApDaemon!ThpStop`，包括主工作线程等待和析构 |
| `0xE617` | 设置门面的已停止标志 `0xB2118` |
| `0xE652` | 调用 VHF 停止函数 `0x147A0` |
| `0xE657` | 调用 `Usb_Stop`（`0x139E0`） |
| `0xE65C` | 调用 `SpiMonitoringStop`（`0xD800`） |

`Usb_Stop` 到 `0x13A25` 才设置 USB 退出标志，在 `0x13A2F` 调用
`CancelIoEx(handle, nullptr)`，随后无限等待两个线程句柄，再关闭它们。
`SpiMonitoringStop` 则清除自己的运行标志、取消 I/O、等待监控线程并关闭句柄。
这两条路径确实有等待，但都排在算法收尾之后；SPI 监控线程与
`SpiModule.x64` 内正在进行的设备请求也不能视为同一个访问者。

**等待 USB 主线程不包含它已经派生的通知线程。** 门面 `0x13B70` 的线程函数执行
六次 `ApDaemon!ThpNotify`，每次之后 `Sleep(200)`，没有读取停止标志。
USB 分发中的一个创建点是 `0xF1DF`，随后 `0xF219` 调用 `0x1BE44`；后者仅
`CloseHandle`，没有等待，相当于 detach。SPI 状态处理路径 `0xCD10` 也创建同一函数，
在 `0xCDF7` 关闭线程句柄。因而关闭 USB/SPI 监控线程本身不能证明通知已全部结束。

`ApDaemon!ThpNotify` 在 `0x4414` 检查 `0x161740`，并不是停止开始时置位的
`0x161742`；前一个标志到 `ThpStop` 等待结束的 `0x43D3` 才置位。
随后 `0x4427` 读取根对象指针，遍历对象 `+0x538..+0x540` 的子对象列表，调用
子对象虚函数 `+0x128`，整个入口没有取得根对象生命周期锁或引用。
主工作线程则在 `0x3A7F` 清空全局根指针，随后析构对象。
这允许以下交错，清空全局指针本身不能防止它：

1. 通知线程通过检查，已经取出根对象或子对象地址。
2. 主工作线程清空全局指针，开始销毁对象及其同步资源。
3. 通知线程继续访问先前取得的对象。

在已核对的子对象虚表 `0x124E28` 中，`+0x128` 指向 `0xFA490`：它锁定
对象 `+0x1D98` 的 pthread mutex、广播 `+0x1DA0` 条件变量并递增计数。
这说明通知最终会接触对象内的同步资源；该局部 mutex 不能保护取得对象之前的生命周期。
这是可以从代码确认的同步缺口，但尚未用异常线程的完整栈证明它就是此前某次崩溃的触发者。

**AFE 关闭并非直接解除映射。** `himax!thp_afe_close` 在 `0x28DD9` 先调用
`thp_afe_stop`，然后等待并释放 `0x198550` 的 mutex，之后才解除映射、清空
`0x184380`、关闭映射句柄和 mutex，调用 `SpbModuleDeInit`，最后卸载动态加载的 SPI 库。
`SpbModuleDeInit` 的函数指针由 `GetProcAddress` 名称与 `0x173500` 槽位对应确认；
调用及卸载点分别为 `0x28EDC`、`0x28EF5`。
因此单个正常 close 调用中的 stop 发生在 unmap 之前，不能把 `0x6A1F` 的异常
直接解释为“同一线程先 unmap 再 stop”。还需区分并发访问、重复收尾或初始化失败状态。

`thp_afe_stop` 的实际停机分支先两次调用 `hx_set_raw_data_type`（`0x2C2BC`、`0x2C2CF`），
再调用 `SpiIntOpen(0, 0)`；非零返回时 `Sleep(1)` 后重试，循环没有本地超时。
后续根据前面结果调用 `SpiIntClose(0)` 和 `SpiIntClose(1)`。
这段设备收尾也可能阻塞，不能把全部长尾都归给前面的持锁休眠。

**已有 SPI 异常位置属于设备请求路径。** `SpiModule.x64.dll_unloaded+0x1F8B`
对应 `GetOverlappedResult(..., TRUE)` 返回后的指令；`+0x26D7` 位于 `SpiWrite`，
`+0x2986` 位于 `SpiFullDuplex`。它们不是已经确认的“中断回调入口”。
结合模块被记录为 unloaded，这支持继续追踪在途请求与卸载的交错；事件日志本身
还不能还原卸载者、在途调用者及当时寄存器，不能据此指认某一线程。

宿主源码另有两个放大窗口：`StopService` 的加载检查、`ThpFuncStop`、`Unload`
没有统一同步，SCM handler 与父进程看护都可进入；`HostController::Stop` 正常路径
只等 SCM STOPPED，不等原进程退出。`Module` 析构只调用 `Unload`，不是再次调用
`ThpFuncStop`，因此不能把三个入口笼统称为“三次停止”。这些源码风险尚未与上述
原厂进程的异常逐一关联，也不能单独解释原厂程序自身的错误。

当前应修复的约束是：先禁止新通知，等待已派生通知及设备访问者退出，再析构和卸载；
外层等待超时必须保留失败状态，不能以正常停止继续释放。仅把 USB 停止提前仍不足够，
因为已经 detach 的通知没有被纳入等待。下一次针对性采样应记录 `ThpNotify` 进入/退出、
AFE stop/close、SPI 卸载的线程 ID 与先后次序，并捕获故障寄存器和完整栈。

## 崩溃后的自愈边界

服务进程被强制终止（接管态）后的时间线：

```
  137 ms   服务消失，THP 宿主还在
 2217 ms   THP 宿主退出（它等父进程句柄）
 5198 ms   SCM 按 SC_ACTION_RESTART 拉回服务
 5777 ms   HuaweiThpService RUNNING
 7499 ms   托盘续租，重新接管
```

0.137 到 5.198 这 5 秒没有任何提供方在驱动设备。

自愈依赖 SCM 的恢复动作，而它配置为 24 小时内 3 次（`ServiceEntry.cpp`）。配额之外没有兜底：
在没有恢复动作的服务上重复同一实验，90 秒内 `svc=STOPPED hw=STOPPED thp=0` 没有任何变化。
用户报告的「触摸失灵，华为驱动也没启动上」就是这个状态。

两处相关的配置事实：

- `ChangeServiceConfig2W` 只写了 `SERVICE_CONFIG_FAILURE_ACTIONS`，没有写
  `SERVICE_CONFIG_FAILURE_ACTIONS_FLAG`。默认 `fFailureActionsOnNonCrashFailures` 为 FALSE，
  因此服务以错误码正常停止（启动失败走的正是这条路）不触发恢复动作。
- `HuaweiThpService` 自己配了 3 次重启、延迟 1 秒，启动类型 AUTO_START。它被我们停止属于正常
  停止，不触发它自己的恢复动作。

## 托盘续租的抖动

24 分钟连续采样，每分钟一条汇总：

```
n=60  avg=999 ms   max=1012~1017 ms     稳态
少数峰值：1083 / 1108 / 1326 / 1927 ms
```

托盘心跳是 UI 线程上的 `WM_TIMER`，周期 1000 ms。最坏一次 1927 ms，离 5000 ms 超时还有很大
余量。同期唯一越过警戒线的两次都是服务自己占住控制线程造成的（4888 ms 和 5129 ms），托盘那侧
没有迟到。

**租约超时的真正压力来自服务自身的同步切换，不是托盘卡顿。**

## THP 宿主没有可用的活性信号

宿主运行约 30 分钟累计 CPU 5.98 秒；静止 5 秒采样，8 个线程的 CPU 增量全部为 0，全部处于
Wait。THP 链是中断驱动的，进程内部没有周期性节拍，因此宿主无法自发产生反映触控链状态的心跳。
`THP_Service.dll` 只导出七个函数（`ThpFuncStart`/`ThpFuncStop`/`GetMESSAGE` 与四个 Register），
不提供任何状态查询。

结论是宿主判活只能停留在进程级：`egoAlive` 现在检查进程是否存在，短期内没有更强的判据可用。

## 面板断电会让宿主内部死亡

一次息屏与唤醒的完整记录：

```
15:06:05.679  DISPLAY_STATE = 0 -> DisplayOff
15:06:12.249  THP host stopped              2 s 去抖 + 4.5 s 停止耗时
15:06:12.253  provider state=6 (EGoSuspended)
15:07:20.402  DISPLAY_STATE = 1 -> DisplayOn
15:07:20.463  Pen host is not responding (running=1, exit=-1); restarting it
15:07:21.984  THP host started
15:07:21.988  provider state=3 (EGoTouch)
```

倒数第三行是关键：pen 宿主在唤醒瞬间被判定为进程还在（`running=1`）而心跳已停。这是「面板断电
之后宿主进程存活、内部已死」的直接证据，它之所以能被发现，是因为 pen 宿主有心跳，而 THP 宿主
没有（见上一节）。

所以挂起时主动停掉 THP 宿主是必要的，不是保守做法：那是在用「主动停」绕开「发现不了」。

## 据此确定的设计

**租约的 deadline 从真正开始持有算起。** `AcquireOrRenew` 原先在进入时设 deadline，随后在同一
调用里同步跑完可能超过整个租期的切换，控制线程返回后紧跟的 `Tick` 会立刻判定超时。真机上这
表现为接管成功 4 毫秒后被自己撤销，随后重新接管，来回 15 秒：

```
15:14:28.462  state=3 EGoTouch            接管成功
15:14:28.466  state=4 SwitchingToHuawei   4 ms 后自己撤销
15:14:33.383  state=2 SwitchingToEGo      下一拍续租，从头再来
15:14:38.268  state=3 EGoTouch
```

**挂起时交还华为，不保留零提供方状态。** `EGoSuspended` 期间两个提供方都不在跑，实测一次息屏
即达 68 秒；`Tick` 与 `AcquireOrRenew` 都对该状态短路，退出它只有 `OnResume` 一条路，Resume 事件
一旦丢失就无限期停住。用 0.32 秒把华为请回来换掉这个状态。`TouchProviderState::EGoSuspended`
作为跨进程 ABI 保留在枚举中，不再发布。

**宿主看护的条件是「华为正被我们停着」，不是「我们持有租约」。** 租约超时会先清掉
`m_hasLease` 再切换，切换失败回滚后宿主将不再被任何人看护，而此时托盘通常已经不在。

**宿主在父进程消失时把华为请回来。** 它是这条路径上最后一个活着的进程，运行在 LocalSystem 下，
`RunHosted` 本来就分得清「被要求停」和「父进程没了」两种来路。这样不依赖 SCM 的次数配额，零
提供方窗口从 5 秒压到 2 秒出头。

## 未解决：本服务停止后原厂服务会跟着停

本服务在**未接管状态**下停止时，`HuaweiThpService` 会在约 3.4 秒后停止，机器随之失去触控，
直到重启（它是 AUTO_START）才恢复。

日常看不到这个现象，因为接管状态下停止会走 `restoreHuawei`，那一步把原厂服务**启动**了，
正好盖住它。托盘没有运行时（登录界面、用户关掉主开关、卸载）才会暴露。

已经排除的：

| 怀疑对象 | 排除依据 |
|---|---|
| 安装程序 | 卸载日志里只有 `ServiceControl(OpenEGoHubService, Action=2/8)`，没碰过原厂服务 |
| Restart Manager | 它的会话在原厂服务停止前 1.5 秒就已关闭 |
| 原厂自我修复 | 原厂服务停止的那一刻，最近 20 秒内没有任何华为进程启动 |
| 服务触发器 | `sc qtriggerinfo` 报告未注册任何启动或停止触发器 |
| 原厂服务自身空转 | 单独启动后连续 60 秒稳定运行 |
| 崩溃（未充分排除） | 当时 WMI 给出 `ExitStatus=0`，SCM 先标记 STOPPED、进程 2.6 秒后退出；10 月实验已证明这些现象不能排除原生异常，该项需结合对应时刻的 Application Error 复核 |

定位到的范围：**强杀本服务进程不会停原厂服务，正常停止会**。

```
taskkill /F    原厂服务 18 秒内一次状态变化都没有
sc stop        原厂服务 +3419 ms 变为 STOPPED
```

两者的区别只有本服务自己执行的那段停止代码。而协调器在这条路上是短路的——停止时的服务日志里
没有任何 provider 记录，说明 `SwitchToHuawei` 在 `state == Huawei` 时直接返回，没有调用过
`stopEGo`、`restoreHuawei` 或 `disableHuawei`。`BtHidChannel::Stop` 也只是取消 IO、join 线程、
关闭句柄，不发任何 MCU 命令。

所以下一步要查的是停止路径上剩下的部分：`StopPenSubsystem` 里 hal 宿主的停止方式（stop 事件
与父进程消失两条来路在厂商 DLL 清理上的差异）、`DeviceRuntime::Stop`，以及句柄关闭顺序。

在查清之前，退出前做任何补救都是无效的：原厂服务是在本服务进程**退出之后** 1.3 秒才停的。

## 复现方法

```powershell
# 服务时序：停掉两个自研服务后单独测华为
sc.exe stop HuaweiThpService ; sc.exe start HuaweiThpService

# 崩溃恢复：接管态下强杀服务进程，按 250 ms 采样服务与宿主状态
taskkill /F /PID (Get-CimInstance Win32_Service -Filter "Name='OpenEGoHubService'").ProcessId

# 宿主线程画像：需要提权，进程属 LocalSystem
Get-Process GaokunThpHost | ForEach-Object { $_.Threads }

# 电源事件序列：直接读服务日志
Select-String 'Power|System event|Provider' C:\ProgramData\OpenEGoHub\logs\OpenEGoHubService.txt
```

租约抖动需要在服务侧临时记录续租的到达间隔。基准点要取上一条命令处理完成的时刻，而不是它到达
的时刻：`AcquireOrRenew` 会同步跑完整个切换，按到达时刻计算量到的是服务自己忙，不是托盘迟到。
